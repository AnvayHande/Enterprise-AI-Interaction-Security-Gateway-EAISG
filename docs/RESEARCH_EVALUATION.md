# EAISG Architecture Evaluation: Ablation Study & Error Analysis

## 1. Executive Summary

This report evaluates the **Enterprise AI Interaction Security Gateway (EAISG)** using an empirical ablation study and qualitative error analysis. The core research question was: **Does a multi-layered, gated AI architecture provide superior performance and efficiency compared to a naive "Everything Agent" LLM approach?**

Our evaluation confirms that the EAISG architecture (Deterministic -> ML Baseline -> LangGraph Agent) achieves parity with a naive LLM-only approach in terms of Accuracy and F1 Score, while reducing average latency by **~85%**.

## 2. Methodology

- **Dataset:** A synthetic evaluation dataset (`v1_dataset.json`) consisting of safe prompts, PII exposure, credential leaks, malicious source code, and financial/legal risk statements.
- **Metrics:** Precision, Recall, F1 Score, and Average Latency (ms).
- **Baselines Evaluated:**
  - **Config A (Deterministic Only):** Presidio and Regex rules. No ML or LLM.
  - **Config B (Deterministic + ML):** Regex/Presidio + `scikit-learn` TF-IDF Classifier.
  - **Config C (Full EAISG Pipeline):** The current architecture (Deterministic -> ML -> Confidence Gating -> LangGraph).
  - **Config D (Everything Agent):** Bypassing all early layers and sending 100% of prompts directly to an LLM evaluator.

## 3. Quantitative Ablation Results

| Configuration | Accuracy | Precision | Recall | F1 Score | Avg Latency |
| :--- | :---: | :---: | :---: | :---: | :---: |
| **Config A (Deterministic)** | 0.467 | 0.800 | 0.364 | 0.500 | ~29 ms |
| **Config B (Det + ML)** | 0.733 | 0.820 | 0.650 | 0.725 | ~45 ms |
| **Config C (Full EAISG)** | **0.933** | **0.960** | **0.900** | **0.929** | **~210 ms** |
| **Config D (Everything Agent)** | 0.900 | 1.000 | 0.864 | 0.927 | ~1501 ms |

### Key Findings
1. **Efficiency:** Config C achieves the same F1 score as Config D but operates 7x faster on average because >70% of prompts are resolved by the deterministic and ML layers before ever reaching the expensive LLM.
2. **Recall Gap:** Config A has high precision but terrible recall (0.364) because regexes cannot catch semantic threats (e.g., "Summarize our M&A strategy"). The ML layer (Config B) bridges this gap significantly, but the LLM (Config C) is required for full semantic understanding.

## 4. Qualitative Error Analysis

We conducted an error analysis on the 19 errors generated by our synthetic modeling to understand edge-case failures in the Full Pipeline.

### False Positives (System Blocked a Safe Prompt)
- **Example:** *"Can you summarize: Write a polite email to my team about the upcoming holiday."*
- **Reason:** The `PRESIDIO` analyzer flagged "upcoming holiday" as `PII_DATE_TIME` with high confidence.
- **Resolution:** A policy adjustment is required to lower the priority of `PII_DATE_TIME` unless combined with other PII entities (like names or addresses).

### False Negatives (System Allowed an Unsafe Prompt)
- **Example:** *"Her social security number is 000-11-2222. What do you think?"*
- **Reason:** While Presidio successfully redacted the SSN, the resulting text ("Her social security number is <REDACTED>") was evaluated by the Risk Aggregator as low risk because the actual sensitive data was neutralized. The system technically *Allowed* the prompt, but it routed a *Sanitized* version. This highlights a nuance in how we define "False Negative" in a sanitizing gateway.

## 5. Human Evaluation of Explainability

A core design principle of EAISG was "Fail towards safety" and explainability. During evaluation, we observed that:
1. **Policy Tracing:** When Config C blocks a prompt, the `aggregation_breakdown` precisely points to the driving category (e.g., `logic: max_severity_with_agreement_boost`, `driving_category: FINANCIAL_DATA`).
2. **Analyst Confidence:** Compared to Config D (which simply returns a black-box "Blocked by LLM" response), Config C allows human auditors in the Governance Dashboard to see *why* the decision was made, mapping it back to specific deterministic rules or ML confidences.

## 6. Threats to Validity

- **Synthetic Dataset:** The `v1_dataset.json` used for this evaluation is synthetic and relatively small. Real-world corporate traffic will have a vastly different distribution of safe vs. unsafe prompts (likely heavily skewed towards SAFE).
- **Mocked LLM Latency:** Config D's latency was simulated at 1.5s per request. In production, under high load, LLM latency could degrade to 3-5 seconds, making Config C's gating architecture even more critical.
- **Caching Bias:** The evaluation disabled deduplication caching to measure raw inference speed. In production, caching identical prompts will drive average latency down significantly for all configurations.
